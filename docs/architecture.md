# Архитектура denisyuce.com

Этот документ — короткая карта проекта. Она нужна владельцу сайта и новым чатам/разработчикам, чтобы быстро понять, откуда берутся данные, какие файлы можно менять и как сайт публикуется.

## Что это за система

`denisyuce.com` — **статический сайт на Astro**.

- **Astro** — сборщик сайта: берёт страницы, компоненты и данные и заранее создаёт готовые HTML-файлы.
- **Статический сайт** — посетителю отдаётся уже готовая страница. Сервер не собирает её заново при каждом открытии, поэтому сайт быстрый и мало зависит от внешних сервисов.
- **Компонент** — переиспользуемый блок интерфейса, например шапка, подвал, FAQ или список услуг.
- **Layout** — общий шаблон страницы, который окружает её содержимое и формирует `<head>`.
- **Slug** — понятная часть адреса после домена, например `classic` в `/services/classic/`.
- **GitHub Actions** — автоматическая сборочная линия в GitHub.
- **GitHub Pages** — место, где лежит и открывается готовый сайт.
- **Cloudflare Worker** — отдельный небольшой сервер, который получает данные DIKIDI и передаёт проекту проверенный снимок.

Упрощённый путь данных:

```text
DIKIDI → Cloudflare Worker → снимок услуг
                                +
                         настройки из админки
                                ↓
GitHub Actions → проверка → Astro → папка dist → GitHub Pages
```

Astro и браузер посетителя напрямую к DIKIDI не обращаются. Если DIKIDI временно недоступен, опубликованный сайт продолжает работать с последними корректными данными.

## Главные источники данных

| Что | Где хранится | Кто меняет |
|---|---|---|
| Названия вариантов услуг, порядок, длительность, цена, ссылка записи | `assets/data/services-catalog.json` | синхронизация DIKIDI |
| Объединение вариантов в страницы, тексты сайта, адреса и выбранные изображения | `assets/data/services-presentation.json` | админка |
| Исходные PNG услуг | `assets/source/services/` | админка |
| Отзывы | `assets/data/reviews.json` | синхронизация отзывов |
| Старые материалы, тесты и документы | `muscles/`, `notes/`, `quizzes/`, `documents/` | непосредственно HTML-файлы |
| Общий дизайн и логика новых страниц | `src/` | код сайта |

`services-catalog.json` хранит факты внешней системы, а `services-presentation.json` — то, **как эти факты должны выглядеть на нашем сайте**. Их не следует смешивать.

## Как устроены страницы

### Новые страницы Astro

Главная, каталог услуг, страницы услуг и 404 находятся в `src/pages/`.

`src/pages/services/[slug].astro` автоматически создаёт страницу для каждого адреса из настроек услуг. Например, варианты массажа на 55 и 90 минут могут иметь разные цены и ссылки DIKIDI, но один `slug` и одну общую страницу с общим описанием.

Шапка, подвал, FAQ, отзывы, прайс и похожие блоки находятся в `src/components/`. Если один блок нужен в нескольких местах, его следует делать компонентом, а не копировать разметку.

### Старые HTML-материалы

Сотни существующих страниц мышц, заметок, тестов и документов пока не переписаны на Astro. Маршрут `src/pages/[...path].astro` читает их исходный HTML, сохраняет содержание и заменяет старую шапку и подвал общими компонентами.

Это переходный слой: старые материалы продолжают работать внутри новой общей сборки без рискованного массового переписывания.

## Услуги и админка

Админка меняет редакционные настройки и PNG-исходники через GitHub. При следующем деплое:

1. загружается свежий проверенный снимок DIKIDI;
2. `tools/services_catalog.py` проверяет связи между услугами и настройками;
3. `tools/export-astro-data.py` создаёт `src/generated/services.json` для Astro;
4. прайс, карточки и отдельные страницы строятся из одного набора данных.

Поэтому цену или название DIKIDI не нужно вручную повторять в нескольких местах. Новая услуга без настроек не ломает сайт: остаётся последний корректный снимок, а ошибка должна появиться в админке и уведомлениях.

Короткие ссылки админка создаёт как `url/<slug>/index.html`. Они проходят через тот же Astro-маршрут, имеют `noindex` и не попадают в sitemap.

## Изображения

```text
assets/source/services/    исходные PNG — главный источник
        ↓
assets/services/           WebP для сайта
assets/meta-services/      PNG нужного формата для внешних каталогов
```

- `site/` содержит общее изображение объединённой страницы услуги.
- `catalog/` содержит изображения конкретных вариантов для внешних площадок.
- `tools/convert-service-images.py` создаёт WebP для сайта.
- `tools/generate-meta-services-feed.py` готовит PNG для каталогов.

Astro сам изображения не придумывает и не создаёт вторую систему обработки. Выходные WebP и PNG генерируются из одних исходников.

## `<head>`, SEO и sitemap

У новых страниц `<head>` создаёт `src/layouts/BaseLayout.astro`. Он получает от страницы заголовок, описание, canonical (официальный основной URL), изображение и структурированные данные. Open Graph- и Twitter-теги отвечают за красивый предпросмотр ссылки в мессенджерах и соцсетях.

У старых страниц исходный `<head>` сохраняет `src/layouts/LegacyLayout.astro`. Если в нём нет данных для предпросмотра ссылки, layout автоматически дополняет их из существующих `title`, `description` и canonical.

Breadcrumbs, или хлебные крошки, описывают место внутренней страницы в структуре сайта. На главной их нет, потому что выше неё нет другого уровня. На внутренних страницах видимые крошки и JSON-LD (подсказка поисковику о структуре данных) создаются самой страницей или сохраняются из старого HTML.

`tools/generate-sitemap.py` читает уже собранные HTML-файлы. Sitemap — это список доступных поисковику страниц. В него попадают только индексируемые страницы с canonical; 404, служебные ссылки и страницы с `noindex` исключаются.

## Какие папки являются временными

- `src/generated/` — данные, подготовленные для Astro;
- `public/` — только публичные файлы, подготовленные перед сборкой;
- `dist/` — полностью готовый сайт для публикации;
- `services-feed.xml`, `meta-services-feed.xml`, `sitemap.xml` — генерируемые файлы.

Их не редактируют вручную: следующая сборка перезапишет изменения. `tools/prepare-public-assets.py` специально собирает чистую папку `public/`, не публикуя внутренние настройки, снимок DIKIDI и исходные PNG.

## Как происходит публикация

Сборка запускается при изменении ветки `main`, вручную и ежедневно после обновления данных Cloudflare.

1. GitHub устанавливает зависимости и инструменты изображений.
2. Конвертирует изображения.
3. Получает и проверяет снимок DIKIDI.
4. Создаёт внешние фиды.
5. Astro собирает готовый сайт в `dist/`.
6. Генерируются sitemap и проверки.
7. CSS и JavaScript уменьшаются по размеру.
8. `dist/` целиком публикуется в GitHub Pages.

Если любой обязательный шаг падает, новая версия не публикуется. Предыдущая рабочая версия остаётся доступна.

## Что лежит в `tools/`

| Файл | Назначение |
|---|---|
| `services_catalog.py` | общая проверка и чтение данных услуг |
| `sync-services-catalog.py` | получает свежий снимок DIKIDI |
| `export-astro-data.py` | готовит услуги для Astro |
| `convert-service-images.py` | создаёт WebP для сайта |
| `generate-services-feed.py` | создаёт основной XML-фид услуг |
| `generate-meta-services-feed.py` | создаёт фид и изображения для внешних каталогов |
| `prepare-public-assets.py` | формирует безопасную публичную папку |
| `generate-sitemap.py` | создаёт sitemap из готовых страниц |
| `test-services-catalog.py` | проверяет услуги, связи и фиды |
| `test-astro-site.py` | проверяет страницы, маршруты, SEO и состав публикации |

Случайных вспомогательных скриптов здесь быть не должно: каждый оставшийся файл участвует в сборке или её проверке.

## Правила для дальнейших изменений

1. Не редактировать вручную `public/`, `dist/` и `src/generated/`.
2. Общий интерфейс менять через `src/components/` и layouts, а не копиями в каждой странице.
3. Факты DIKIDI не переносить в редакционные настройки сайта.
4. Изображения услуг начинать с PNG в `assets/source/services/`.
5. После изменений выполнять `npm run check`, `npm run build` и тесты из `tools/`.
6. Не сканировать и не копировать `assets/Icon_Pack`: это старая внешняя библиотека, не участвующая в новой сборке.

## Локальные команды

- `npm run dev` — открыть сайт для разработки;
- `npm run build` — подготовить данные и собрать `dist/`;
- `npm run check` — проверить Astro и TypeScript;
- `python3 tools/test-services-catalog.py` — проверить услуги и фиды;
- `python3 tools/test-astro-site.py` — проверить готовые страницы и SEO.
